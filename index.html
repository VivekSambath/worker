Dedicated Worker & Shared Worker

Web Workers basics: what they are, how they work, and when to use which.

Why does the page freeze, and how does a worker fix it?

  • A page runs JavaScript on one main thread, which also handles clicks, scrolling and drawing.
  • A long task freezes the page until it finishes.
  • Worker = a background thread. Heavy work moves there, and page and worker talk only with postMessage. A worker cannot touch the DOM.
Real-world example

You upload a 50 MB CSV into a web app and the page hangs ("Page unresponsive"). With a worker doing the parsing, the buttons keep responding, like a photo editor whose filter runs in the background.

What happens when the main thread is busy?

  • Clicks, scrolling, drawing and JavaScript share one thread.
  • During a long loop, clicks wait in a queue and the spinner stops.

What is a worker, in plain terms?

PM = the page

  • Talks to stakeholders (clicks, scrolling, screen)
  • Must stay free to answer them
  • Only one of them: the main thread

Developer = the worker

  • Works heads-down on the heavy tasks (builds, data crunching)
  • Never talks to stakeholders (no DOM)
  • PM and developer pass written tickets (postMessage)
Real-world example

A PM who codes the whole feature personally leaves stakeholders waiting for answers: the page freezes. If the PM hands the coding to a developer, stakeholders get replies all the time and the developer hands back a ticket update with the result.

Does each page get its own worker, or do they share one?

  • Dedicated (new Worker('worker/worker.js')): each PM gets a personal developer. They stay until that PM's project ends.
  • Shared (new SharedWorker('shared-worker/shared-worker.js')): one PM coordinates every developer (tab) from the same backlog. They work until the last developer's project ends.

How does a Dedicated Worker fit in?

  • 1 page = 1 worker. Private, ends when the page closes.
  • Worker A and B cannot see each other.
Real-world example

An online PDF compressor open in two tabs: each tab compresses its own file in its own worker. One tab's work never slows or changes the other.

What is a Shared Worker?

  • One worker for all tabs of the same origin and script URL.
  • Each tab gets its own port.
  • Lives until the last tab closes.
Real-world example

Web chat open in 3 tabs: one connection receives each message once and pushes it to all tabs. Log out in one tab and the worker tells the others to log out too.

Why use a Shared Worker?

  • One WebSocket / polling timer instead of one per tab.
  • One source of truth: login, cart, notifications stay in sync.
  • One shared cache, less duplicated work.
  • Tab-to-tab messaging through the worker.
  • Watch out: closed tabs are not announced (send a "bye" on pagehide or use a heartbeat), a crash affects every tab, and browser support is uneven.
Real-world example

Stock price dashboard open in 5 tabs: without a shared worker you get 5 live connections to the server, and with one you get 1. A chat app with 3 tabs also shows the same unread count in every tab.

What is inside a worker?

  • Each worker = its own OS thread, event loop, JS heap, global scope.
  • Messages are queued and delivered by the receiver's event loop (async, never blocking).
  • By default nothing is shared: data is copied, like passing a photocopy of a note. For big buffers use transfer: postMessage(buf, [buf]).
  • A worker can use fetch, WebSocket, timers and IndexedDB, but not window, document or localStorage.
Real-world example

A software team: the main thread is the PM talking to stakeholders, the worker is the developer. The developer never joins stakeholder meetings, and requests pass through a ticket queue.

How long does a worker live?

  • Startup costs time and memory: create workers once, reuse them.
  • End it with worker.terminate() (page side) or self.close() (worker side).
  • Shared worker: runs while at least one tab is connected.
  • Only worth it for heavy work: for tiny tasks, thread startup costs more than it saves.
Real-world example

Creating a new worker on every button click: 1000 clicks means 1000 threads and a slow, memory-hungry page. Create one worker at start and send it 1000 messages instead.

How do Dedicated and Shared Workers differ?

Dedicated Worker Shared Worker
Purpose Heavy work, no UI freeze Share state across tabs
Instances One per page One per origin + script
Memory Private Shared by all tabs
Talk via worker.postMessage sw.port.postMessage
Lifetime Until its page closes Until the last tab closes
DOM access No No

Which one should I pick?

  • Slow work in a single page → Worker.
  • Several tabs need the same connection or state → Shared Worker.
  • Only simple tab-to-tab messages → BroadcastChannel is easier.
  • Safari support for Shared Worker has been weakest: check before relying on it.
  • Libraries using workers: PDF.js, Monaco Editor, Mapbox GL JS, TensorFlow.js.
Quick scenario check

Resize 20 photos without freezing the page → Worker.

Same notification count in 5 open tabs → Shared Worker.
